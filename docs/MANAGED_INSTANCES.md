# Managed instances (AutoSEO Cloud)

AutoSEO Cloud (`cloud/`, deployed at https://autoseo.codext.de) sells a private, fully managed AutoSEO instance
per customer. Every customer gets **their own isolated deployment** of the open-source app (own container, own
PostgreSQL, own data volume) at `https://<slug>.autoseo.codext.de`, provisioned through the Coolify API.

The self-hosted app does not depend on any of this. The environment variables below are optional bootstrap
settings: a self-hoster can use them too (e.g. to skip the setup code), but only `DOMAIN` is ever required.

## Instance environment contract

| Variable | Required | Purpose |
|---|---|---|
| `DOMAIN` | yes | Public host of the instance, e.g. `acme.autoseo.codext.de` |
| `DATABASE_URL` | yes (compose sets it) | PostgreSQL connection string |
| `DATA_DIR` | no (default `/data`) | Uploads, caches, `secret.key` |
| `AUTOSEO_OWNER_EMAIL` | no | When set and the instance has no users yet, the first boot creates this user as instance admin + workspace owner and skips the setup code |
| `AUTOSEO_OWNER_NAME` | no | Display name for that owner (default: local part of the email) |
| `AUTOSEO_WORKSPACE_NAME` | no | Name of the first workspace (default `My Workspace`) |
| `AUTOSEO_SMTP_URL` | no | Default outgoing mail server used while Admin → Email is not configured. `smtp://user:pass@host:587` (STARTTLS) or `smtps://user:pass@host:465` (TLS). User and password must be URL-encoded |
| `AUTOSEO_MAIL_FROM` | no | Sender for the default mail server, e.g. `AutoSEO <noreply@autoseo.codext.de>` |
| `AUTOSEO_SSO_SECRET` | no | Enables one-click sign-in from the cloud dashboard (see below). At least 32 random bytes, hex or base64 |
| `AUTOSEO_CLOUD_URL` | no | URL of the cloud dashboard (`https://autoseo.codext.de`). Shows a "Manage subscription" link to instance admins |

Values configured in the admin panel always win over these defaults (e.g. once Admin → Email is enabled, the
instance uses that SMTP server instead of `AUTOSEO_SMTP_URL`).

## One-click sign-in (SSO) token

The cloud dashboard signs a short-lived token with the instance's own `AUTOSEO_SSO_SECRET` (every instance has a
different secret, so a leaked secret only affects one instance):

```
payload = base64url(JSON.stringify({ email, exp, nonce }))   // exp = unix seconds, at most 5 minutes ahead
token   = payload + "." + base64url(HMAC_SHA256(secret, payload))
```

The browser is redirected to `https://<slug>.autoseo.codext.de/auth/sso?token=<token>`. The instance verifies
the signature (timing-safe), the expiry and that the nonce was not used before, then creates a normal session
for the **existing** user with that email and redirects to `/`. It never creates users. Invalid or expired
tokens redirect to `/login?error=sso`.

## Coolify service layout

Each instance is one Coolify *service* (Docker Compose) named `autoseo-<slug>` in the Coolify project
"AutoSEO Cloud", using the prebuilt image `ghcr.io/codextde/autoseo:latest`:

- `app` — the AutoSEO image, domain `https://<slug>.autoseo.codext.de` (set through the `urls` API field),
  volume `autoseo-data:/data`, health check `GET /api/health`
- `postgres` — `postgres:17-alpine`, volume `autoseo-pg`, password generated by Coolify
  (`SERVICE_PASSWORD_POSTGRES`)

Secrets (`AUTOSEO_SSO_SECRET`, `AUTOSEO_SMTP_URL`) are set through the service environment API, never written
into the compose file.

## DNS

- `autoseo.codext.de` → Coolify server (Cloudflare proxied)
- `*.autoseo.codext.de` → Coolify server (**DNS only**, so Traefik can issue a Let's Encrypt certificate per
  customer host; Cloudflare's universal certificate does not cover second-level wildcards)

## Lifecycle

| Event | Instance |
|---|---|
| Checkout completed | provisioned + started, owner gets an email when `/api/health` answers |
| Subscription `active` / `trialing` / `past_due` | running |
| Subscription `unpaid` / `canceled` / deleted | stopped (data kept, can be restarted by resubscribing) |
| Admin "Delete" | service + volumes removed |
